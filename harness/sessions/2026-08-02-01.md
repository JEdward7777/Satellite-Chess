- 23 new unit tests (`test/client-clock.test.ts`). 462 pass, up from 439.

**One real bug found and fixed on the way**: `optimistic.ts` flipped
`clock.active` on a predicted place while leaving `startedAt` alone. Harmless
while nothing drew a clock; the moment one existed it would have shown the
opponent losing the mover's entire think time in a single jump the instant a
piece went down. `predict` now nulls `startedAt` with the flip, so the clock is
shown frozen for the one round trip rather than lying. Tested from both ends —
directly in `optimistic.test.ts`, and through the consequence in
`client-clock.test.ts`.

## What was learned

**The plan drifted from the code and the drift compounded.** `5.1`–`5.3` were
built during phase 4 because a move cannot be applied without banking time,
handing over and re-arming the flag — the work went in, the statuses did not. So
`STATE.md` recommended "phase 5, the clock; the DO half and the flag-fall alarm
are not written" for five consecutive sessions, at a DO half that was written,
tested, and had played a whole game through `drive-game.mjs`. The recommendation
was repeated into each new session file and never re-checked against the source.

The transferable part is the shape, not the instance: **a stage that gets built
incidentally, as a dependency of the stage actually being worked on, is the one
that never gets marked.** Nobody sets out to implement `5.2.2`; they implement a
move, and re-arming the flag comes with it. Worth spending five minutes grepping
for the *next* phase's identifiers before recommending it, rather than trusting
the previous session's "Next" list. That check cost twenty minutes here and
would have saved five sessions of a wrong headline.

**A snapshot's timestamps and the phone's clock are different clocks, and only
one place in the client had noticed.** `net.ts` already converted the opponent's
last fix through `serverNow` and said why in a comment. The clock needs exactly
the same conversion for exactly the same reason, and getting it wrong is worse:
two phones would disagree about whether someone had flagged. `estimateServerNow`
is now the one place that arithmetic lives, and the test that pins it puts the
phone an hour out from the server on purpose.

**Mid-game there is no cheap way to make the server re-send a snapshot**, which
is what made the low-time driver hard. `onPos` broadcasts a bare `opp_pos` to the
*other* phone and only broadcasts state when the handshake changes something, so
a phone walking around receives nothing new. The first attempt drove the player
around the board expecting a fresh frame and timed out. The driver now keeps the
last raw `state` frame and re-delivers it with one number changed — which is also
the better instrument, since the balance is the only lie and the timebase stays
the server's.

**Ten minutes is the shortest time control the app can produce** (decision 0012,
deliberately — the clock pays for walking), so the low-time path is unreachable
by playing. Any future work on time pressure needs the same override hook rather
than patience.

**A `12_000` ms clock does not count in tenths, and that is correct.**
`formatClock` switches at ten seconds. The first driver run failed its own
"tenths actually move" check against 0:11 stepping once a second — the test was
wrong, not the code. Noted because the failure reads like a repaint-rate bug and
the repaint rate had just been changed, which is exactly the wrong place to start
looking.

## Loose ends not worth a stage

- **The clock is not announced when it is the opponent who is low.** Deliberate:
  being buzzed about someone else's time trouble while walking is noise. If
  playtesting says otherwise it is a one-line change in `paintClock`.
- **`arm()` is called on the first tap on the board**, which is the only place a
  mobile browser will let audio start. A player who never taps before their clock
  is low gets vibration and no sound. That player has also not moved a piece, so
  the case is close to hypothetical, but it is the reason the two channels are
  independent.
- **The 100 ms clock repaint runs for the whole game**, not just under ten
  seconds. It touches two text nodes and a class where `paint` redraws the
  canvas, so it was not worth making adaptive — but it is the obvious thing to
  look at if `9.4` (battery) finds a problem.
- **O-11 did not recur.** Fourteen full-suite runs this session, all clean.
