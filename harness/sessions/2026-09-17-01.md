## What was learned

**Every sentence hedges, and that was the whole design problem.** The mapping is
one-to-many in the wrong direction: `bad_token` is six distinct checks in
`auth.ts` collapsed into one code, and `expired` covers both a genuinely timed-out
flow and one whose cookie never came back. So no sentence may assert a cause.
A confident wrong explanation is worse than a bare code, because it sends someone
to fix the wrong thing — turning wifi off and on in a field because we told them
it was the network, when a browser handoff ate the flow cookie. There is a test
asserting the hedge (`/usually|not something you can fix/`) so a later session
cannot tighten the copy into a lie.

**Two codes deliberately get no sentence.** `declined` is something the player did
on purpose — explaining it back reads as an accusation — and `unknown` is the case
where we genuinely do not know. Returning null for both is meaningful: the screen
falls back to "you can try again", which is all there is to say. Inventing a cause
for `unknown` is the exact failure this stage exists to prevent.

**The code stays on screen even now there is a sentence.** It is the only exact
part, and the only part that survives being read down a phone line to somebody who
can open this source. The sentence is what a player acts on; the code is what makes
the failure debuggable. Losing either would be a regression.

**`bad_token` needed a sentence that says "stop trying".** Every other failure is
worth retrying. That one is a server misconfiguration, and without saying so the
screen leaves somebody in a field tapping a button that cannot work, assuming they
are holding it wrong. It has its own test.
