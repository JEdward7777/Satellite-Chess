## What was learned

**The delete case is the whole problem, and it is invisible until there are two
phones.** Pushing what you hold and taking what comes back is four lines and is
wrong: the phone in your pocket re-pushes the field you deleted on the other
phone last week, and it comes back for ever. Nothing in a single list can tell
*"the server has never heard of this"* from *"the server used to hold this"* —
so the journal exists to answer exactly that one question. Every test in
`test/field-sync.test.ts` is really about that distinction. Written up as
decision 0032 because the journal reads as bookkeeping and is the first thing a
tidying session would delete.

**Server-side tombstones were the obvious alternative and are worse for a reason
that is not about correctness.** They are immortal by construction — pruning them
reintroduces the resurrection — so the account accumulates a permanent list of
every field its owner ever deleted, which is a list of places a named person used
to go. Decision 0017's whole point. The journal keeps that on the phone that
already knows it.

**One endpoint rather than REST, on budget grounds.** `POST /api/fields/sync` is
one request whether nothing changed or everything did, and the steady state is a
request with two empty arrays. Five fields over five `PUT`s would be five
requests against 100k/day, and a half-applied batch is a state neither end can
describe.

**A field's `updatedAt` is the dirty flag, which meant only `remove` needed the
journal on the write path.** A save is recognised as pending because its
`updatedAt` no longer matches what was acked; a delete leaves nothing behind to
notice, so it has to leave a note. That asymmetry is why the store wrapper
intercepts one method and passes the other three straight through.

**Two races were real and both are tested.** A rename made *while a sync is in
flight* is lost if the merge compares against the field list the pass started
with — so `syncOnce` re-reads the store after the response. And a delete made in
flight is lost if the journal is rewritten wholesale at the end — so the
tombstones that arrived since are carried over rather than replaced.

**`sync()` must never reject.** Every caller fires it and walks away, so a
throwing local store (private-mode IndexedDB) would surface as a red console line
on a phone in a park for a background task whose failure is already an ordinary
state. It resolves to `{kind: 'skipped', reason: 'local'}` instead.

**A comment in `shared/field.ts` said `FieldOrigin.via` was "never on the wire".**
It now goes to the account. The claim was about the *field link* format, which
still carries only the lineage key and version — corrected in place rather than
left for someone to read as a rule I had broken. The `origin_via` column was
already in the schema from `2.3.1`, so the intent was there.

  in the client establishes a session except the dev seam, so the endpoint 401s in
  an ordinary browser and the phone stays local-only. Designed behaviour, but it
  means the feature goes unexercised outside drivers until phase 2 finishes.

## Loose ends not worth a stage

- **O-13** opened: a field the server refuses is re-pushed on every sync, for
  ever, because it never gets a journal entry. Deliberate — acking a field the
  account does not hold would make the *next* sync delete it locally — and the
  cost is a few hundred bytes on a phone holding a corrupt field. The fix, if
  `rejected` ever turns out to be non-empty in practice, is a `refused` map
  beside `acked`.
- `MAX_FIELDS_PER_ACCOUNT = 200` is a wall, not a quota: it stops an
  authenticated client using its own Durable Object as a database for something
  else. A field already held is still updatable at the cap, so a full account is
  not a read-only one.
- The `fields` upsert keeps `MIN(created_at)` on conflict, because a copy taken
  on a second phone is the same field and did not come into existence twice.
- `SURVEY_SECRET` is `field-walk-2026-a7k3m9qx`, unchanged.
