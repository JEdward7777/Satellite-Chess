## What was done

- **Decision 0023 — reach absorbs GPS error, and squares scale with it.** The
  owner's ruling: the reach circle is the safety net for imprecision, and if the
  fix is not precise enough we make the circle bigger. That is already what
  `effectiveReachM` does, so nothing needed building; what was missing was the
  stopping point, and that is the half worth recording. A circle that grows past
  the square it selects stops requiring a walk, and the walk is the game — so
  worse GPS means *bigger squares and a bigger field*, not a tighter circle. The
  ratio is the playability constraint, not either number alone.

## What was learned

**The optimistic layer did not need chess.js, and that was not obvious.** The
instinct is that predicting a move requires a rules engine. Measured: chess.js
adds **35.8 kB to a 44.7 kB bundle**, which is the exact cost `render.ts:376`
already refused once. The whole layer came to **3.5 kB** instead, because of an
asymmetry worth remembering — **the client never generates moves, it only applies
one the server already declared legal.** A place's destination came from
`carry.destinations`. So applying it needs only the three cases where the board
changes somewhere other than `from`/`to`: castling, en passant, promotion. None
of the FEN bookkeeping matters either, since `piecesFromFen` reads the placement
field and whose turn it is comes from `clock.active`.

**A lift is the one act that genuinely needs move generation**, because the
server refuses to lift a piece with no legal moves. So it is predicted *without*
destinations — and that costs nothing, because **the next act of a move is a walk
away**. Dots that arrive 200 ms after the lift are invisible to someone about to
spend thirty seconds getting there. The latency worth removing is
tap-to-acknowledgement, not tap-to-complete-information. This is a general point
about this game: optimism is cheap here in a way it would not be in a game played
with a thumb.

**Hold the pending action, not the predicted result.** The first shape was to
compute a predicted snapshot and merge later snapshots into it, which needs a
rule for what wins. Holding the *action* and re-applying it on top of whatever
the server last said makes the server's snapshot always the base, and turns
reconciliation into a question of evidence: does this snapshot show the carry we
asked for? Doing it by `rev` instead would flicker every time the opponent bumped
the revision by offering a draw, which says nothing about our lift.

**An empty destination list is a usable sentinel**, because the server never
sends one — `onLift` refuses `no_legal_moves` rather than carrying an empty set.
So "provisional" needed no new wire field and no client-only flag on a shared
type. It does mean that invariant is now load-bearing in two places; both are
commented, and a test asserts the view's half.

**Predict only what is certain.** Showing a move and snatching it back is worse
than the wait it was hiding, so `predict` returns null for anything it cannot be
sure of and the action still goes to the server unchanged. Confirmed in the
browser: tapping on the opponent's turn produces *no* local carry at all, and
then the server's "It is not your turn."

**Screenshots earned their keep again, and so did the fix-rate trap.** The first
driver run looked like a reach bug — "You are 28.3 m from e2" while standing on
e2. The simulator emits a fix once a second, so a tap dispatched immediately
after a teleport still carries the old position. STATE.md warned that a click
teleports *and* taps; it did not warn that the teleport takes a second to be
believed. Both are now in the driver's header and in STATE.md.
