## What was learned

**The service worker would have swallowed sign-in entirely, and nothing would
have said so.** `sw.js` answers *every* in-scope navigation from the cached
shell, and `/auth/google/login` is a navigation. For any returning visitor —
which is everyone with the app installed — tapping "Sign in" would have rendered
the cached home screen, the redirect to Google would never have happened, and
there would have been no error in any console. This is **O-10**, which three
sessions had assessed as benign, becoming load-bearing the moment a server route
was reached by navigation rather than by `fetch`. Found by reading `sw.js` before
deploying rather than by losing an afternoon in a browser. Fixed with a two-line
prefix exclusion and a driver assertion so it cannot come back.

The transferable rule is narrower than O-10 itself: **any new server route
reached by navigation must be excluded in `sw.js`**, and there is now one line
where that list lives.

**The inherited-constraint pattern claimed a third victim, and this one had been
sitting in a file for six weeks.** `container.md` says flatly that
`wrangler deploy` and KV namespace creation are impossible and lists `2.4` as
the operator's. True of the ephemeral container; false on the operator's WSL
machine, which the file conceded only in a closing parenthesis. The namespace
took about ten seconds. Previous sessions found the same shape twice (playwright,
then "`2.1` cannot be finished in a container"), and the lesson had been written
down both times — but written down *next to* the stale claim rather than on top
of it. So the framing was rewritten this time: `container.md` now opens by saying
which machine it is about, and `STATE.md` points at that rather than repeating it.
**A correction only works if it is in the place the wrong thing is read from.**

**One wrangler quirk worth keeping:** a bare `wrangler kv namespace list` fails
with "Authentication error [code: 10000]" even with `workers_kv (write)` on the
token. It needs `CLOUDFLARE_ACCOUNT_ID` set explicitly; the error names the wrong
cause. `deploy` and `secret list` need no such help. That one error message cost
more time than the rest of the KV work combined.

## Half-finished

**Nothing is half-written, but one thing is unproven**: the code exchange itself.
Everything around it is tested — the redirect's parameters, PKCE, state, nonce,
the session that comes out — and the exchange needs a human at a Google consent
screen, which no test in this project can be (decision 0034). So
`redirect_uri_mismatch` and consent-screen surprises remain unfalsified until
someone signs in on the deployed origin. The recipe is in `STATE.md`.

`auth.ts` redirects failures to `/?signin=failed&reason=…` and **nothing renders
that yet** — deliberately, it is stage `2.5.3`. Until then a failed sign-in lands
silently on the home screen.
