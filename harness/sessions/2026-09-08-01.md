## What was done

Built the game index, and the thing it turned out to need first.

**`3.5.2`, which was not on the plan for today.** `2.3.4` is titled "a
cross-device resumable game list", and half an hour in it became clear that
without this it is a cross-device *readable* list: `GameDO.join` matches a player
by the UUID in one browser's `localStorage`, so the second phone is a third
player and gets `game_full`. A list of games you can see and cannot enter is
worse than no list, because it reads as a bug in the game rather than as a
missing feature. `seatFor` in `index.ts` is the whole fix — a session names the
player, the body's `playerId` is honoured only when there is none — applied
identically at create, join and the WebSocket upgrade.

**The index itself**, as **decision 0033**: written by `GameDO` over the `USER`
binding at every state change, and by nothing else.

- `src/shared/game-index.ts` — the entry, the claim arithmetic (`claimStateFor`,
  the same rule as `GameDO.suspensionFor`), the removability rule
  (`forgetIsRefused`), and the sort. Shared so the phone and the Worker cannot
  disagree about whether a month has passed.
- `src/worker/user-games.ts` — the row codec. Deliberately *not* a validator, and
  the file says why at length: nothing on this path came from a phone.
- `UserDO.recordGame` / `dropGame` / `listGames` / `forgetGames`.
- `GameDO.syncIndex` — builds one line per seated account entirely out of stored
  columns, so it is deterministic and a digest in `meta` skips an unchanged push.
  Called at create, join, start, pause, disconnect-suspend, resume and finish.
  **Not on a move.**
- Two routes: `GET /api/games`, `POST /api/games/forget`. Game schema 3 adds
  `white_account` / `black_account`.
- `src/client/games.ts` (transport, never rejects), `src/client/views/games.ts`
  (the list's words and the tidy screen), and the "Your games" section on home.

## What was learned

**The direction of a sync is a design decision, not a detail, and the answer here
is the opposite of last session's.** `field-sync.ts` was finished a day ago and
the obvious move was to mirror it — the phone pushes, the server merges. It is
wrong for games, and the reason is worth keeping: a field genuinely originates on
the phone (walked out with no account and no signal, decision 0013), and a game
genuinely does not. Following the symmetry would have put a client-writable
endpoint under `2.3.5`'s permanent record, which is the one thing that record
cannot survive — a result the player can POST to themselves is a note of what
they felt like claiming. Distance is already client-reported (O-03) and that is
tolerable exactly because the hard facts around it are not.

The tell that the direction is right: **none of `field-sync.ts`'s apparatus is
needed here.** No journal, no acked map, no "the server has never heard of this"
versus "the server used to hold this". All of that exists because the phone is
the origin of a field.

**A denormalised index has to say when it refreshes, or it silently becomes a
per-move cost.** Pushing on every move would have handed straight back the saving
that denormalising the columns bought — the point of them is that ten games list
without waking ten Durable Objects. So the rule is "at state changes", and the
thing it costs is an accurate `lastMoveAt` on a game you are in the middle of
playing, which is information for finding a game you have lost.

**The digest needed the entry to be deterministic, which is why `joined_at` is
not in `GameIndexUpdate`.** The first shape had the game supplying it, and it
moved on every push — so no digest ever matched and the guard did nothing. The
account stamps it once on insert and the upsert never touches it again;
`GameIndexUpdate` is `Omit<GameIndexEntry, 'joinedAt'>` to make that a type error
rather than a convention.

**The countdown has to be computed from both sides, and `claimableInMs` only has
one.** `claimStateFor` answers "when may *you* claim", so it is zero for the
player who caused the suspension — correct as a statement of rights, useless as a
countdown, and that player is precisely the one who needs telling that a clock is
running against them. The view measures the window from `suspendedAt` instead,
with the same shared constant. This is the sort of thing that looks identical in
a screenshot, which is why it is in `test/game-list.test.ts` rather than left to
a driver.

**"Never remove a claimable game" resolves to "never remove one that is not
over".** A suspended game stays claimable for ever once the month is up, so
reading the stage literally makes a suspended row permanent — and that is the
right answer, not a degenerate one: the join code is the only handle on the game
(decision 0007), so deleting the row destroys the only route either player has
back to something that can still be decided. The exits are the ones decision 0025
already designed — claim, or resign — and both are inside the game.

**A forgotten game comes back if you open it again.** Re-taking a seat forces a
push past the digest. That started as a self-heal for a push that failed once and
whose next transition might be a month away, and it doubles as the honest answer
to "I tidied this away and then walked back into it".

- `MAX_GAMES_PER_ACCOUNT = 1000` is a wall, not a quota, and it refuses only a
  *new* row: a full index must not freeze the game somebody is playing.

  removable, where guessing "in play" would pin a row that may be nothing at all
  in place for ever.
