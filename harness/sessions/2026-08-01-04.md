## What was learned

**An independent decoder is the only thing that can vouch for an encoder.** A
wrong QR encoder produces a tidy square of dots. Unit tests written by the
encoder's own author check that it agrees with itself, which is worth very
little. `check-qr.mjs` decodes 351 symbols with jsQR — every version boundary
from 1 to 14, all four levels, UTF-8 — and jsQR has never seen this code. The
unit suite then holds a snapshot of one symbol jsQR read back correctly, so a
regression fails `npm test` offline. That ordering is the point: the fixture is
trustworthy *because* the script vouched for it first, not the other way round.

**And a correct QR is still not a scannable one.** That is a genuinely separate
claim, and it is why `check-invite.mjs` screenshots the rendered symbol and
decodes the pixels. Between a correct matrix and a camera there is an SVG, a
stylesheet, a `<figure>` with a background colour and a device pixel ratio, and
each can produce something perfect on paper and unreadable in practice — a
transparent QR over this app's near-black chrome is dark-on-dark; one bled to the
edge of its box has no quiet zone; one left antialiased has soft module edges.
All three look fine to a person.

**The browser check found a real bug, and it was not in anything new.** The
create screen offers a handicap, so the driver asserted the resulting reach on
the board: expected 12.0 m, got 10.0 m. `reachNow()` in `game.ts` had been
calling `effectiveReachM(accuracy, cfg)` with **no bonus argument** since phase 4.
The server was applying the handicap correctly all along — it is in `checkCarry`,
in the start-zone test, and in the snapshot as `PlayerView.reachBonusM` — so the
symptom is not "handicapped moves are refused". It is worse and quieter: the
screen tells a handicapped player a move is out of reach when the server would
accept it, and they believe the screen and walk further than they needed to. No
test caught it because nothing had ever created a game *with* a handicap; there
was no UI to do so. Fixed as `myReachBonusM`, exported and unit-tested, reading
the bonus from the snapshot rather than from the create screen — the joining
phone never sees that screen, and decision 0004 turns on both players seeing the
same circle.

That is the third time on this project that a browser driver has found something
every unit test missed. The pattern is now specific enough to state: **a control
that sets a value is also the first thing that ever exercises the value.**

**Alphanumeric QR mode is a trap here, and it looks like free money.** It packs
11 bits per character pair against byte mode's 8 per character — a 25×25 symbol
instead of 33×33 for a typical invite. It needs the payload uppercased, which is
harmless for `/j/CODE` and destroys the base64url blob in the `/f/<blob>` field
links of stage 6.4. Written down in decision 0024 rather than left as a comment,
because the density difference is visible to anyone looking at the symbol and the
reason not to take it is not.

**`querySelector<HTMLSelectElement>` does not compile under
`tsconfig.tools.json`.** `HTMLSelectElement` redeclares `remove()`, and in the
one config where the DOM and Workers globals coexist the merged `Element` already
has HTMLRewriter's, which returns an `Element` rather than `void`. The errors
name `remove()` and HTMLRewriter and have nothing to do with the code — exactly
the failure mode decision 0021 predicts. Every earlier view only ever asked for
inputs and buttons, which do not redeclare `remove`, which is why this took
until now to appear. Selecting untyped and casting the event target sidesteps it.

**`npm install --no-save` prunes.** Installing jsQR removed Playwright and then
installing Playwright removed jsQR, which reads as "the script is broken" rather
than "the package is gone". Install them in one command.

## Loose ends and judgement calls

- **The invite screen tears down the WebSocket and re-opens it.** Coming back to
  the QR from the board closes the connection; going to the board re-opens it.
  The alternative is an overlay keeping the board alive underneath, which is more
  machinery for a screen nobody looks at for more than a few seconds, and the
  reconnect path already exists and is exercised. If reconnection ever becomes
  expensive, this is the caller to change.
- **The mailto tier is not driven in a browser.** Clicking it in a headless Linux
  container hands a `mailto:` to nothing observable. The ladder itself is covered
  in `test/share.test.ts`; `check-invite.mjs` drives the two tiers that are real
  in a browser (clipboard, and a stubbed share sheet).
- **`MAX_HANDICAP_M = 4` is a bound on the control, not a rule.** The server
  still accepts any non-negative integer from a hand-rolled `POST /api/game`.
  **O-02** updated to say so — that observation is now reachable rather than
  theoretical, since there is finally a UI that sets a handicap.
- **Decisions 0023 and 0024 were missing from `decisions/README.md`.** 0023 was
  never indexed by the session that wrote it; both are there now.
- **O-09 was not opened.** Four sessions running. `carry.test.ts` was not touched
  this session either, and the named race in the suspension tests is still there.
