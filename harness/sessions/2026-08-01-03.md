## What was learned

**The observation described the smaller half of the bug.** O-06 said the asset
paths were relative. True, and irrelevant on its own: `/j/ABC123` was a **404**
from the assets binding, so the browser never got as far as resolving `app.js`.
Fixing the paths without teaching the Worker the routes would have changed
nothing at all, and the fix would have looked done.

**`env.ASSETS.fetch('/index.html')` is a 307 to `/`.** The assets binding's
default `html_handling` strips `index.html`. The browser follows the redirect, so
the app does load — at `/`, with the join code **gone from the URL**. That is the
worst possible shape for this bug: the next stage reads the code off the path,
finds nothing, and every symptom points at the client's parser while the Worker
looks correct. Found by curling `wrangler dev`, not by testing.

**The test passed against that bug.** `SELF.fetch` follows redirects by default,
so `expect(res.status).toBe(200)` was true and the body was the right shell. The
assertion is now `{ redirect: 'manual' }`, and that flag is the entire value of
the test — this is a case where the naive version is not weak, it is actively
misleading. Worth remembering for anything else that asserts on a status code
from `SELF.fetch`.

**`cache.add('/index.html')` was going to be the next casualty**, for the same
reason: a redirect is not a document. The shell is now precached and matched as
`/`, which is where the server actually serves it. One key, one URL, no
disagreement between the precache list and the navigation lookup.

**`register('sw.js')` resolves against the document, not the worker.** So the
phone that scanned the QR — the one standing in a field, most likely to be
offline — is precisely the one that would have registered nothing. No error, no
console message: `registerServiceWorker` already swallows failures on purpose.

**The load-time 404 was `/favicon.ico`.** Noted as a loose end for two sessions.
The shell named no icon, so Chromium guessed. One `<link rel="icon">` and the
driver run is now clean of 404s and console errors, in every context — which is
worth more than the minute it cost, because "no 404s" is only a useful assertion
once it is true.

**Install is now all-or-nothing for the things that matter.** It used to swallow
every failure per entry, which was right for icons and wrong for the bundle: a
cache with no `app.js` in it would have replaced a working one. `CRITICAL` is
`addAll`, `OPTIONAL` is best-effort, and `activate` prunes only after install
resolved.

## Loose ends and judgement calls

- **The service worker answers navigations the Worker would 404.** Logged as
  **O-10** rather than fixed. The SW serves the shell for *any* in-scope
  navigation; the Worker serves it only for real routes. Once the SW is installed
  it decides, so `/nonsense` is a 200 for a returning visitor and a 404 for a new
  one. Narrowing it means either duplicating `parseAppRoute` inside `sw.js` — it
  is served raw and cannot import — or building `sw.js` from TypeScript, which is
  a fourth runtime and so a fourth tsconfig under decision 0021. Both are real
  work on a guess about which behaviour is better, and offline the broad rule may
  simply be right. `check-deeplink.mjs` asserts the divergence so it stays a
  decision rather than becoming a surprise.
- **The service worker now skips `/api`.** Two lines, slightly outside O-06.
  Nothing does a GET to the API *yet*, but `6.2` will, and a cache-first game
  state served from disk would be a genuinely nasty bug to diagnose in a field.
- **The client does not yet act on the route.** `parseAppRoute` has one consumer.
  Deliberate: `6.2.1` is where a deep link opens the game, and this stage was
  scoped to making the shell load at all. The app currently shows home at
  `/j/ABC123`, which is the correct *loading* outcome and the wrong *routing*
  one. Do not read `6.0` as `6.2.1` being done.
