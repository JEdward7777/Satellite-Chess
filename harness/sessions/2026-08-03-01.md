## What was done

Camera scanning, and the decision not to ship a decoder for the browsers that
cannot do it.

- **`src/client/scan.ts`** — the model half. `detectScanSupport` (asked once at
  boot, because the answer needs `await` and the home screen repaints on every
  GPS fix), `scanAdvice` for the browsers that cannot, `codeFromScan`, and
  `startScan` over `BarcodeDetector` + `getUserMedia`.
- **`src/client/views/scan.ts`** — the viewfinder, with the typed-code box on it
  as well as on home, because the fallback belongs where the failure happens.
- **`main.ts`** — a Scan button only where scanning works, the advice line where
  it does not, and `showScan` routing a scanned code through the same `showJoin`
  a deep link and a typed code take.
- **`scripts/check-scan.mjs`** — the sixth browser driver, 18 checks.
- 27 unit tests (`test/scan.test.ts`). **503 pass**, up from 476.

## What was learned

**The bundle question was settled by measuring it, and the number was worse than
the plan assumed.** `6.2.4` said "measure the WASM bundle before committing".
Measured: the whole app is 74 KB minified / 27 KB gzipped, and jsQR — the
*pure-JS* option, no WASM in it at all — is 128 KB / 45 KB. Nearly twice the
application, precached by the service worker onto a phone in a park on one bar,
to save an iPhone user from either typing six characters or using the Camera app
in their hand. Decision 0026 records it, including the part that is easy to get
backwards: this was never a Cloudflare cost. A decoder is a static asset, run on
the phone, outside the Worker bundle and outside the 100k requests/day. It fails
the *player's* byte budget.

**`codeFromScan` is a filter before it is a parser.** A camera swept across a
park sees posters, bus stops and other people's wifi credentials. The interesting
case was `/f/<blob>`: a field link *does* parse as an app route, so a looser check
would have joined a game whose code was a field's blob. It is tested explicitly.

**A foreign QR must not read as a failure.** At four looks a second, a scanner
that says "scan failed" every time it sees a menu is lying to the player
continuously. `scanStatus` treats it as information — "that is a QR, but not an
invitation" — and a real failure outranks it.

**Releasing the camera is the part that needed a test, and the nasty case is the
teardown during the permission prompt.** Clearing `srcObject` turns nothing off;
only `track.stop()` does. If the player taps Back while `getUserMedia` is still
waiting on the prompt, the stream arrives with no screen left to display it and
nothing to stop it — a lens left on, invisible to every assertion about scanning.
`startScan` returns its stop function synchronously so a not-yet-open camera can
still be shut, and `check-scan.mjs` asserts `readyState === 'ended'` on real
tracks from Chrome's fake device.

**A screenshot of a working viewfinder read as broken.** Chrome's fake camera is
a dark rolling pattern, so the first screenshot looked like a black box, which is
exactly what a broken viewfinder looks like. `videoWidth > 0` did not settle it
either — that says the stream has dimensions, not that anything is painted. The
answer was to read pixels (luminance 45–117, so real variance), and that check is
now in the driver. Same lesson as `opponentDot()` in `drive-game.mjs`: when the
question is about what is on screen, measure the screen.

**One thing looked like a bug and was not.** The Back button on the scan screen
sits under the fixed simulator panel until the page is scrolled. Measured rather
than assumed: `[data-cancel]` at y=720, panel at y=708, and 142 px of available
scroll. It is a `?sim=1`-only overlap — there is no panel on a real phone — so
nothing was changed for it.
