## What was learned

**A single lock made of "nobody sets this variable" is a lock made of everybody
remembering.** The survey API is gated on a secret alone and that is right for
it — worst case, an exposed debug log. This endpoint mints a session for any
account, so its worst case is total authentication bypass, and the plan's own
words were "never reachable in a deployed build". A convention cannot deliver
that. The second lock — a loopback hostname — was chosen specifically to be one
that a *mistake* cannot open: setting a secret on the wrong Worker is an ordinary
slip, and making a deployed Worker answer to `localhost` is not.

**The lock has to guard reading, not just minting.** The mint route is the one
that looks dangerous, so it is the one a naive implementation gates. But a token
minted against a local build would then keep working against a deployed build
that happened to share the secret. `identityOf` re-checks both locks before
honouring a `d1.` token, and that case has its own test.

**A test caught a real gap in the implementation it was written for.** `asSub`
accepted `..`, because `.` is in the charset and the charset was the whole rule.
A Durable Object name is hashed rather than used as a path, so it was not the
traversal it looked like — but an account key made entirely of punctuation is
never a real Google `sub`, and excluding a category costs nothing before anything
depends on it. Fixed the implementation, not the test.

**A shell environment variable does not reach a Worker, and the symptom is
indistinguishable from working correctly.** `DEV_AUTH_SECRET=… npx wrangler dev`
starts cleanly and the seam 404s — which is exactly what the seam looks like when
deliberately switched off on purpose. Cost a confused round trip.

**And the obvious fix for that was a trap.** `.dev.vars` is the ecosystem-standard
answer and it was written, used, and then removed again, because **`wrangler types`
reads `.dev.vars` too.** With the file present, the generated `Env` gains
`DEV_AUTH_SECRET: string` and `npm run types:check` fails against the committed
`worker-env.d.ts`; without it, it passes. A gitignored per-developer file was
deciding whether a committed artifact was up to date — so `npm run check` would
pass or fail according to who ran it, which is worse than the problem it solved.

`--env-file` pointing at an empty file does suppress it, but in wrangler 4.114
that flag is array-typed and swallows the positional output path, so
`wrangler types --env-file=x path/out.d.ts` writes to `worker-configuration.d.ts`
in the project root instead. Not worth fighting. The variable is now passed on the
`wrangler dev` command line (`--var`), where `wrangler types` cannot see it and
`wrangler deploy` cannot carry it — which also makes the "off in production" lock
structural rather than a matter of what is in someone's untracked file.

That does mean the local dev value is committed in `package.json` and is not
confidential. It costs nothing: the deployed build's protection is that the flag
is absent, not that the value is unknown, and the value alone only guards a
loopback dev server full of invented accounts. Said plainly in the README rather
than left to look like an oversight.

**`npm run check` failed on a fresh clone for a reason that had nothing to do
with the code.** Three tests assert the shell only references assets that exist,
and `public/app.js` is a gitignored build artifact — so a clone that has not run
`build:client` fails a gate that AGENTS.md §7 makes mandatory before pushing. A
gate that cries wolf on a clean tree teaches people to push through it. `check`
now builds the client first.

**`pkill -f "wrangler dev"` matches the shell running it.** Killed my own command
mid-verification. Obvious in hindsight, and the reason the second attempt used a
fresh port instead.
