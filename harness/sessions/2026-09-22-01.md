**The distance number, which was the real work (`2.3.5.3`).**

`presence.travel_m` was `MAX(travel_m, reported)` over a counter that lives as
long as the *page*: it included the calibration walk, the walk to the park and
every earlier game in the same sitting, and a reload froze it. Carrying that into
a permanent row would have made the headline wrong from the first game. It now
credits by difference, per `leg` (one per page load), only while `active`, capped
at `MAX_PLAUSIBLE_SPEED_MPS` over a window that cannot be banked, and every leg
is re-baselined at the transition into `active` (`startIfBothReady`).

## What was learned

1. **A rate cap does not subtract meters.** Capping the first post-start report
   at 12 m/s left the pre-start walk in, because the gap before that report is
   long enough that the ceiling never binds: measured **+12 m leaked into a 57 m
   game**. The fix is re-baselining at the one transition into `active`, not a
   tighter cap.
2. **Do not hook that on `last_clock_start_at` being newer than the last
   report.** That column is re-stamped every ply, so it would zero the credit of
   whichever player had not relayed since the last move — a per-ply under-count
   worse than the leak. `startIfBothReady` is the only place the transition
   happens, and it covers the start *and* every resume.
3. **The residue is a constant per active period, not a percentage.** The
   reviewer walked the same four moves seven times as far: 15.3 and 15.6 m lost
   out of 58.5 m walked, and 13.0 and 12.2 m lost out of 400.7 and 390.5 m. It
   is about one accumulator hop — `max(4 m, 2 × claimed accuracy)` — at each end
   of the active period, so a real game is **1–3% short, one way**. Quoting it
   as "25% at a jog" from the short driver run was the wrong unit and the wrong
   impression.
4. **The owner's real games are already on the deployed app**, played
   2026-09-20, and they hold a pre-rule `travel_m`. Since the record ships in
   the *same* deploy, none of them has pushed a line yet, and `join()`
   re-pushes a finished game's — so they would have written the inflated number
   into a permanent row. Hence `travel_m` is nullable and
   `travel_leg IS NULL AND travel_m > 0` records them as **unmeasured**: listed,
   never counted, no date and no migration flag.
5. **A real socket left idle while a test sleeps is a flake.**
   `net-integration.test.ts` failed 2 of the reviewer's 4 runs. `connectToGame`
   already takes `now`, so the client's floor is now driven by an injected
   clock and the server's stored instants are moved with a helper; that test
   sleeps not at all, the file went from ~7.4 s to ~2.5 s, and five runs pass.
   **One 1.6 s sleep remains** in the opponent-dot test in the same file, which
   was not touched.
