## What was learned

**6.3 was not the change I expected, and the server was the easy third of it.**
The field was already snapshotted at creation and already in every `GameSnapshot`
on the socket; returning it from `join` is four lines. The actual blockers were
both on the client and neither was about fields:

- `showHome` sent a phone with no saved fields **straight into calibration**. So
  the one phone that needed to type a code — a friend who has just been handed
  one across a field — could not reach a screen with a box on it. Home is now
  shown either way, with New game hidden (that genuinely does need a field).
- Which then made calibration something you can walk into by choice rather than
  the first run, so it needed a way out that is not "save a field". It had none:
  `CalibrateDeps` had `onSaved` and nothing else.

Neither is visible from the stage description, and neither would have been found
by testing the join API.

**A request outlives the screen that fired it.** The joining screen has a Cancel
button, for the slow-network case it exists for — and cancelling did nothing,
because the promise resolved a few seconds later and called `enterGame` on top of
whatever the player had moved on to. Found by looking at a screenshot of the
screen and asking what its own button did. The fix is a `live` flag cleared by the
screen's teardown, which `swap` already calls at exactly the right moment. Worth
remembering as a shape rather than a bug: any screen that starts a request and
then lets you leave has this.

**O-09 was two races, and the second one was O-07 all along.**

- *The suspension tests* raced the runtime, as the observation described. The fix
  is `closeAndSettle`, which waits for the object to have scheduled its own
  `disconnect` deadline before bringing it forward. The observation proposed
  polling `presence.connected = 0`; that is **not quite enough** — `onDisconnect`
  writes presence *first* and schedules afterwards, so presence going to zero
  still leaves a window where the object's deadline lands after the test's and
  replaces it. Waiting for the timer row is the correct signal.
- *"Lets both players move in turn"*, unexplained for four sessions, was the O-07
  pattern in a test written before the pattern was understood: black waited for
  "a carry exists" while black's buffer already held the broadcast of **white's**
  lift. It matched instantly, `walked()` backdated a row that did not exist yet,
  and black's place was refused as a teleport. Reproduced three times in eleven
  runs, then fixed by routing the test through `move()`. Eight consecutive clean
  runs of the worker project afterwards.

The lesson is in how it hid: it is *the same bug* in an older test, so looking for
a third mechanism was looking for something that was not there. When two
instances of a pattern are found and fixed, grep for the pattern rather than
declaring it handled.

**A driver that forbids all 404s cannot test a feature whose job is to produce
one.** `check-deeplink.mjs` uses `/j/ABC123` — well-formed, no game — as a shell
test, and 6.2.1 turned that into a real request that correctly 404s. Three checks
failed on the feature working. Rewritten to assert the positive: the client asks
about the code in the path, and says there is no such game. The offline run got
the better half of it — a deep link with the network cut now asserts the screen
blames **the network** rather than the code, which is exactly the distinction
`join.ts` exists to make and could not have been checked any other way.

**Chromium logs every non-2xx fetch as a console error**, so any driver that
provokes a failure on purpose needs to filter `Failed to load resource` out of
its console-error check, or it fails on its own assertions.

## Loose ends not worth a stage

- **A joiner does not keep the field they played on.** Deliberate: handing someone
  a copy of ground they have never stood on, as a side effect of accepting an
  invitation, is a choice rather than an obvious convenience. Noted under `6.3`
  and belongs with `6.4`, which is about sharing fields on purpose.
- **`createGame` still uses `alert()`** for its failures. The join path no longer
  does — a typed code that cannot be one now gets the same screen as every other
  failure — so create is the last caller. Not changed here because a failing
  *create* is a different conversation (usually a field the server refused, which
  needs re-choosing) and it would have meant a third screen for no evidence.
- **O-10 updated, not closed.** Its revisit trigger was `6.2.5`, which is now
  done. The two behaviours do diverge — a returning visitor gets the home screen
  at `/j/SHORT` where a first-time visitor gets a 404 — and the divergence is
  benign, so it stays open and unfixed with the finding written down.
- **O-07 updated** with the third instance, and the note that its own
  "make it structural if a third appears" trigger has arguably been met. The
  `rev` floor is still the answer if a fourth turns up.
- **O-11 opened, and it is an admission rather than a finding.** One
  `npm run check` reported `1 failed | 438 passed` *after* the O-09 fixes, and I
  lost the name to a `tail`. Twelve subsequent full runs were clean, two of them
  under 2x CPU oversubscription, so I could not reproduce it either. The one hard
  fact is that the failing run took 69 s of test time against a normal 18–30 s,
  with `wrangler dev` and a browser driver alongside it, and the worker tests wait
  on a 2 s wall-clock timeout. Logged so the next thread reads a recurrence as a
  known unknown rather than as O-09 coming back — and so it captures the whole
  output next time instead of a tail.
