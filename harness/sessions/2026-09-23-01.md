### Settled — do not re-litigate

1. **PGN positions are board space, never lat/lng.** A PGN travels through a share
   sheet; coordinates in one would disclose where somebody regularly stands
   (decisions 0017/0018, and 0040's no-coordinates rule for the record). A board
   index has no anchor, so it is unlocatable by construction.
2. **One canonical PGN per game** — no seat tag, no names, nothing reader-specific,
   so `8.4` can archive a single blob. The opponent is never named.
3. **The join code is in neither the file nor the filename** (O-34). The filename is
   `satellite-chess-YYYY-MM-DD-<field-slug>.pgn`.
4. **Fetch at mount, share on tap.** `navigator.share` dies if anything is awaited in
   front of it (`gotchas.md`), so the screen loads the report on mount and holds it.
   Ladder: share sheet with `files:[File]` → share sheet with text → clipboard →
   a visible `<textarea>` plus a plain `<a href="/api/game/:code/pgn">`, which is a
   *server*-initiated download and therefore survives where page-initiated blob
   downloads are blocked. **No `mailto` tier** — a whole PGN in a mail body is wrong.
5. **`travel_m` null ⇒ unmeasured**, carried through to an omitted tag and a sentence
   on screen. The predicate `travel_leg IS NULL AND travel_m > 0` (0040 rule 7)
   wants factoring out of `GameDO.recordLine` into `measuredTravelM(travel_m,
   travel_leg)` in `src/worker/travel.ts`, used in both places.

## What was learned

**The reviewed-until-clean loop earns its cost, and every phase needed it.** Across
three phases, nine review rounds found: a client that could strand a player on
"checking with the server…" for ever; three separate routes by which one account's
fields could be deleted from a phone when another signed in; a justification in a
schema migration that was simply false; a permanent record about to be filled with a
distance that included the walk to the park; and a test that failed one run in three.
**None of these were found by the agent that wrote the code**, and in every case that
agent had already reported the work as finished and green.

**A reviewer that only reads is not enough.** The findings that mattered most came
from reviewers that *ran* things — the driver on their own server, the flaky file five
times, the same game walked seven times as far. Round 3 of phase 3 stated a residue
with the wrong sign because nobody had re-measured it; round 4 measured it and the
number was not merely wrong but backwards.

**Ask what a number scales with before believing it.** Phase 3's under-count looked
like 25–50% of a 57 m test stretch and would have undermined `2.3.5`'s headline. It is
a **fixed cost per active period** — one accumulator hop, `max(4 m, 2 × claimed
accuracy)` — so the same four moves walked seven times as far lost the same 13–16 m.
A real game of several hundred metres is 1–3% short, one way. Both figures are now in
`travel.ts`, `gotchas.md` and decision 0040 with the measurements behind them.

**Second opinions changed three decisions and caught one trap.** The obvious way to
close the pre-start leak — re-baseline whenever `last_clock_start_at > last_pos_at` —
would have zeroed the credit on the first relay after *every ply*, because the clock
start is re-stamped on every move. The second opinion caught that before it was
built. It also chose `unmeasured` over zeroing the operator's real games, and chose to
fix the 401 journal reset rather than merely log it.

**`npm test` had a flake and it blocked a commit.** `test/worker/net-integration.test.ts`
failed about one run in three: it slept ~4 s in real time and the socket was torn down
underneath it. Fixed with an injectable clock (`connectToGame` already took `now`), so
the file also dropped from ~7.4 s to ~2.5 s. **Run `npm test` twice** until there is
reason to trust it again.

### What it decided, that the checklist did not anticipate

1. **The time control had nowhere to come from.** The `game` table stores what is
   *left* on each clock plus the increment; nothing remembered what the clocks
   started at once a move had been played. Hence `game.initial_ms` and schema 5,
   written on create, backfilled on upgrade **only when no move has been played**
   (where it is exactly right) and left NULL otherwise. So `GameReport.initialMs`
   is `number | null` and the PGN writes the standard's `TimeControl "?"` for null.
   **The operator's two real games will read `"?"`.** This is the only change to
   the contract of the two shared files that were called settled.
2. **`report()` returns `you: Color`, not `Color | null`** — the route always passes
   `identity.sub` and a non-seat is refused, so null there would be a dead state.
   The nullable form belongs in the client, where `body.you` off the wire is
   validated down to `'w' | 'b' | null`. The door `8.4` needs is
   `private buildReport(game)`, which has no reader to check.
3. **Seat refusals answer 404, not 403**, so the route tells a non-player nothing
   about whether a code names a real game. O-34 already gives away enough on `peek`.
4. **The client builds the PGN itself** at mount with `buildPgn(report)` — that is
   what makes "no await before `navigator.share`" achievable. The `/pgn` route
   exists only for the bottom rung of the ladder.
5. **`PGN_LEGEND` had to be tokenized.** Pushed whole it produced a 143-column line,
   which falsified the 80-column promise in its own docstring. A new test caught it.
   Any future long comment pushed as one token will do the same.
6. `SCHEMA_VERSION` is informational — recorded in `meta`; the real upgrade is the
   `pragma_table_info` branch in `upgradeGameTable`. **A backtick inside a SQL
   template literal breaks the build**, so SQL comments in `schema.ts` must not
   contain one.
